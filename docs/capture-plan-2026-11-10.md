日期：2026-11-10。用户已同意第一批，并补充 OCR 应尽量免框选，可评估复用 `D:\RAG\ocr` 的 MinerU。本次更新 OCR 交互与复用方案，不表示这些行为已经实现；第一批授权保留。

翻译、词库和知识包的完整审查见[翻译审查](translation-review-2026-11-10.md)。本文件补充取词部分，优先级在领域知识库之前。

**实施更新**：第一批源码已按后续批准落地，结果与验证边界见[0.6.5 交付记录](first-batch-2026-11-10.md)。下文保留方案形成时的审查记录；当前明确无选区、超时、禁止和取消均不继续复制。OCR/IA2 尚未实施。

## 1. 将目标改成可以验收的行为

“任何情况 100% 获取准确原文”无法保证。普通应用不一定暴露选区；图片没有文本层；OCR 会误识别；受保护画面可能无法截图；密码框、安全桌面、提权窗口和 denylist 还受现有产品规则限制。微软也明确说明 UI Automation 受权限与 UIPI 边界约束。[微软安全说明](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-securityoverview)

建议目标是：

- 有真实文本选区且接口可读：优先读取原文，不先截图。
- UIA 不可用但能复制：提供用户已启用的受控复制回退，以及用户主动复制的入口。
- 普通画面中无文本接口/无可复制文本：优先复用可信的可见选区坐标；没有坐标时，鼠标指向目标后按一次取词快捷键，识别当前文字块。手动框选仅是复杂版面的备用入口。
- 受保护或禁止读取：明确结束，不继续尝试剪贴板/OCR 绕过。
- 每次尝试给出“成功/无选区/不支持/超时/被阻止/需 OCR”等可理解的状态；不能无声失败。

OCR 是新增的主动识别入口，不应把普通悬停改成后台截图，也不能声称 OCR 恢复了屏幕外的完整选区。微软 Text Extractor 的官方说明也要求校对 OCR 输出。[官方说明](https://learn.microsoft.com/en-us/windows/powertoys/text-extractor)

## 2. 从现有代码确认的问题

以下取词问题主要来自静态审查，未在目标应用逐项人工复现；与翻译报告中已运行的模型/词典诊断区分。

| 位置 | 现状 | 体验或风险 | 建议 |

| `MouseHook.cs`、`App.xaml.cs:446` | 鼠标轮询不会产生 Wheel；部分失效依赖鼠标移动才检查 | 滚动/静止切换窗口时，旧选区/浮层可能残留 | 监听前台/窗口生命周期和可用的滚动、选区事件；未覆盖时主动失效，不能使用陈旧快照 |

不要通过扩大到整个文档范围来“提高成功率”。那可能取得未选中的全文，违反产品定义。剪贴板里有新文本，也不能单凭这一点认定它就是本次选区：某些编辑器无选区 Ctrl+C 会复制整行，其他程序也可能改剪贴板。

### 文档中的 UIA 线程要求需要修正

design.md §6.2 和 AGENTS.md 写独立 STA。微软对桌面 UI Automation 客户端及其事件管理的建议是独立、无窗口的 **MTA** 线程，事件添加/移除还需保持线程安排一致。[微软线程文档](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-threading)

因此不应该把“Task.Run 改成 STA”直接当修复。实施时先更新技术决策，再按当前 .NET/WPF/UIA 实际调用验证独立 MTA；剪贴板 OLE 的 STA 需要与 UIA 分开看待。

## 3. 推荐的最小取词链

```text
用户选中 + 悬停 / 取词热键
          ↓
总开关、前台、密码/安全桌面/提权/denylist 检查
          ↓
UIA：聚焦/光标及祖先 → 有界备选 → 一次延迟重试
          ↓ 仅“不支持/无结果/超时”等可回退状态
IA2：仅当实测表明能显著补足目标应用时实现
          ↓
受控剪贴板：用户已开启；可备份；前台/选区证据成立
          ↓
有可信的选区行坐标且已启用 OCR → 可见选区局部 OCR
          ↓ 没有可信坐标 / 仍失败
明确失败状态 + 主动操作入口
       ├─ 我来复制：用户 Ctrl+C 后主动读取当前剪贴板
       └─ 指向识别：鼠标放在文字上 → Ctrl+Shift+D → 局部 OCR → 当前文字块
```

“我来复制”是用户主动触发的一次读取，不是常驻剪贴板监听；适合应用能复制、但模拟复制不可靠的情况。指向 OCR 是热键主动触发的新语义，需要在实施时更新 product.md/design.md；自动路径仍必须有真实选区与停留证据，不能因为文字读取失败就把任意拖动当成选区。

### 必要的数据变化

复用 `SelectionSnapshot`；新增最小的捕获结果状态，例如 `Success / NoSelection / Unsupported / Timeout / Forbidden / ClipboardUnavailable`，而不是继续全部返回 null。结果带来源、耗时、几何是否精确及语言无关的错误码；读取文字失败但已有可信行坐标时保留坐标，OCR 成功后生成快照。区分真实选区与推断文字块，不能用截图框边界冒充精确文字选区。

UIA/剪贴板/OCR 通过已有设计中要求的 `ISelectionCapture` 接口连接；`Capture` 只取内容，不翻译。App 仅发起/取消并展示状态。以本次工作所需的最小接口实现，不先开发插件市场或全应用适配框架。

### 超时与进程隔离

第一步使用单个 UIA 工作者与有限队列，旧任务失效后不再排队；看门狗超时后立即给出可操作的下一步。必须承认阻塞 COM 调用可能仍未结束，不能靠持续 `Task.Run` 堆积线程。

如果目标应用测试确实出现长期挂死，且需要无需重启应用就恢复 UIA，再把该执行器放入小型辅助进程，通过管道返回快照，超时只重启自己拥有的辅助进程。不是第一步就重写全部捕获模块，也不能误杀其他应用。

## 4. OCR 改为免二次框选

### 4.1 用户只记一个动作

| 情况 | 用户动作 | 应用行为 |
|---|---|---|
| 原文接口可读 | 照常选中、停留 | 读取原始字符，不经过 OCR |
| 选区存在、行坐标可信，但文字读取失败 | 已启用 OCR 后，无额外动作 | 在原有停留触发条件成立时，仅识别这些可见行区域，原位显示结果并标 OCR |
| 图片、扫描 PDF、自绘内容，没有可信选区 | 鼠标指向目标段落，按现有 `Ctrl+Shift+D` | 先尝试正常取词，失败后识别光标附近文字块；短暂描边，让用户看见处理范围；无需先框选、再点确定 |
| 双栏、表格、代码密集区，目标不明确 | 必要时点击候选文字块 | 保守返回光标所在块；不能稳定定位时才提供手动框选备用，不擅自串入相邻栏 |

原文入口不要求每次确认。常驻面板内可展开 OCR 原文检查/纠错，悬注维持只读；低把握结果明确提示。截图限于当前可见区域，无法恢复屏幕外文字时说明范围。重复热键关闭当前结果、Esc 取消等现有习惯保持。

不要增加“启动 OCR → 进入截图模式 → 框选 → 确定 → 翻译”的常规流程，也不新增一排模式按钮。没有真实选区时，按热键就是用户明确指定识别光标附近的动作；普通移动、悬停、点击不后台 OCR。OCR 启用与安装仍由用户显式操作，模型不自动下载。

### 4.2 现有鼠标坐标能做什么

`App.xaml.cs` 已记录按下/抬起坐标，并以大于 4px 判为拖动；`MouseHook` 有移动事件，但目前没有文字选区轨迹模型。起止两点不能证明有选区，也不能准确还原跨行、反向、双栏、滚动中的选择。**不能直接用两点组成的矩形当 OCR 选区**，否则容易漏掉中间行、带入邻栏，甚至把拖动窗口当成选字。

优先让 `UiaSelectionReader` 分离文字与坐标读取。目前它先 `GetText(-1)`，空文本就跳过，未保留之后可能取得的行坐标。确有非空选区与有效可见行坐标时，这些坐标才可支持自动 OCR；若 provider 连选区/坐标也不暴露，转到热键指向入口。拖动信息最多用于显式识别时排序候选，不能成为自动截图的唯一依据。

指向入口先截取前台客户区内、光标附近的有限区域，运行文字检测，按光标命中、行对齐、行间距和栏间空白组合当前文字块；必要时有界扩大一次。优先按文字行块处理，不先引入 PDF 版面大模型。初期以段落块为主，不承诺仅凭指针就能知道用户想要哪个词或几句话。检测不到就明确失败，不自动截完整桌面反复重试。多屏负坐标、DPI、遮挡及页面滚动后失效均需验证。

这是交互建议及待验证的算法，尚未在真实截图上证明段落定位准确率。若密集版面误取较多，优先保留“一键识别当前行”的保守行为，而不是牺牲范围准确性追求自动整段。

### 4.3 本地 MinerU 的复用结论

已只读检查 `D:\RAG\ocr\mineru`。目录中存在 `mineru-4.0.6-released.zip`，但当前 `src/mineru/version.py` 写的是 **4.0.5**；不能按压缩包名称认定正在使用的源码版本。

| 已有文件 | 可复用能力/限制 |
|---|---|
| `src/mineru/model/ocr/pp_ocr_v6_onnx.py`，`PPOCRv6ONNX` | 可直接接收图片，返回检测框、文字、分数；无需先把截图转成 PDF 或跑全文档解析 |
| `models/MinerU-4_models_onnx/OCR/paddleocr/ch_PP-OCRv6_tiny_det_infer.onnx` | 检测模型 1,780,590 字节 |
| 同目录 `ch_PP-OCRv6_small_rec_infer.onnx` | 识别模型 21,159,378 字节；两模型合计约 22.94 MB，不含运行时及其他依赖 |
| `src/mineru/model/ocr/data/ppocrv6_dict.txt` | 配套字符表 74,947 字节，必须与识别模型匹配 |
| `src/mineru/model/runtime/onnx.py` | 此处普通 OCR 路径明确使用 CPUExecutionProvider；不能因为整套 MinerU 装了 CUDA 就声称截图 OCR 已用 GPU |
| `PPOCRv6ONNX.ocr` / `_det_rec` | 默认 drop_score=0.5，低于阈值会过滤整条检测结果；完整性很重要的代码可能因此缺行，需要对本地候选单独验证、保留低分提示，不能静默漏掉 |

推荐先复用现有本地模块做独立截图质量验证，不启动 MinerU 的 PDF/表格/公式/VLM/Gradio 全链路。通过之后才提取必需的 OCR 推理及前后处理组件，或采用已验证支持该模型的轻量适配；不复制整个 `.venv`、不让发行版依赖 `D:\RAG` 的绝对路径，也不修改现有 RAG 环境。

首次验证可从 E 盘的隔离辅助进程只读调用已有 Python 环境和模型，显式禁止下载与原文/图片日志，检查是否有模块导入副作用。正式便携分发再选择最少的独立运行组件；**23 MB 模型不代表完整 Python OCR 包也只有 23 MB**。不能为避免 Python 就立即手写整套 C# 预处理/解码，那会把现成能力变成新的维护负担。

此本地封装依赖几何处理、图片预处理、后处理和字符表，并非复制一个 `.py` 就能独立运行。其注释还写明不支持角度分类，模型实际支持的语言与小字号/代码效果必须实测；不将注释中的语言范围当成已验证覆盖。

本地 `LICENSE.md` 与当前上游均是 **Apache 2.0 加附加条款**，`pyproject.toml` 标为 `LicenseRef-MinerU-Open-Source-License`，不能按纯 Apache 2.0 直接处理。复用源码时保留对应许可与署名；模型权重来源和再分发许可需单独复核。[上游原始许可](https://github.com/opendatalab/MinerU/blob/master/LICENSE.md)

### 4.4 GitHub 参考与引擎选择

- [Text Grab](https://github.com/TheJoeFin/Text-Grab)：WPF/.NET、MIT，可参考屏幕坐标、窗口与 OCR 分工。它的 Windows OCR 路径可作为低依赖基线；WinAI 路径要求 Copilot+ PC 等条件，不能作为全部 Win10/11 用户的默认依赖。不能把 Quick Simple Lookup 当成指向 OCR：其 README 说明那是自定义文本查询。
- [RapidOCR](https://github.com/RapidAI/RapidOCR)：已有 ONNX 与多语言运行时实现，仓库包含 `dotnet`，适合作为轻量部署候选。**尚未验证其当前解码/前后处理可直接加载这里的 PP-OCRv6 权重**，不能承诺换两条模型路径就能接入。
- [selection-hook](https://github.com/0xfullex/selection-hook)：参考跨应用取词回退与每应用过滤，不为此给 WPF 引入 Electron，也不照搬其默认剪贴板/全局键盘事件策略。[发布记录](https://github.com/0xfullex/selection-hook/releases)

本轮建议以现有 MinerU 的轻量 ONNX OCR 做首个质量候选，与 Windows OCR 用同一批截图比较，最终只选一个默认后端；不先同时实现多个引擎和自动切换体系。测试记录准确字符、漏行、串栏、冷启动/热推理耗时、内存和包体积，再决定是否需要独立组件。尚未执行 OCR 推理与性能测试，不承诺亚秒响应。

### 4.5 代码、符号与隐私

OCR 只能补“没有原文接口”的缺口，不能修复已经取得原文后的模型占位符/符号错误。`0/O`、`1/l/I`、反引号、括号、下划线、`<=` 与 `≤` 都需加入截图样本；不使用 LLM 凭语义猜改程序。正确保留识别出的原文和换行，低分内容可检查；OCR 分数只是引擎输出，不等于真实正确率。

截图仅在触发后于本地处理、不默认落盘、不默认发送远端；本地 OCR 结果也不因远程翻译源已配置就偷偷上传截图。若用户配置并选择远程翻译，处理后的文字是否发送依现有明确配置执行。所有后端共用总开关、禁止读取、前台与 generation 校验；无法判断是否属于受限目标时不绕过。截图裁剪区域可能包含邻近内容，应尽量缩小、只翻译选定块，处理完成及时释放。

## 5. 代码场景要拆成三个问题

1. **取不到代码文本**：按取词链修复；能用 UIA/复制时保留原始字符，OCR 作为手动后备。编辑器特殊选区或屏幕外选区必须说明取到的范围。
2. **取到了代码，符号让翻译崩坏**：按翻译审查中的保护/还原与校验修复。URL、反引号、花括号、运算符、版本、下划线不能使全句失效。
3. **代码本身不是自然语言**：标识符、缩进、语法、数字与操作符默认保留。混合英文说明可翻译；完整代码先展示“已识别代码，原样保留”。需要“解释这段代码”时作为单独的主动能力，不能把保留代码误显示成未识别。

首期只可靠处理明确的反引号、围栏代码块等边界；不要试图为所有编程语言写一套推测性解析器。没有边界且判断不清时保留原文、让用户选择解释，避免把变量名翻成中文而生成不可用代码。

## 6. 分批修改、测试和验收

| 顺序 | 修改范围 | 验收 |
|---|---|---|
| 0：失败可见与共同边界 | Core 捕获状态/接口、App 路由、所有捕获后端共用的拒绝检查 | 禁止状态不进入下一后端；每类失败有明确结果；日志无原文 |
| 1：修现有取词 | `UiaSelectionReader`、`ClipboardSelectionReader`、App 触发/取消/事件、受影响设置/文档/测试 | 搜索有界、命中即返回；前台切换/取消无旧结果；剪贴板文本/HTML/图片/文件及用户并发复制不被破坏；终端不误发中断 |
| 1 同步：修翻译链 | 见翻译审查 A/B | NBSP 正确分类；URL/术语/数学样本不出现坏占位符；长文局部失败不丢整段 |
| 2：免二次框选 OCR | 先用已有模型验证局部截图；再接热键、可信行坐标、文字块定位、本地 OCR、可展开原文与来源；同步产品文档 | 普通段落指向后一次热键即可识别，无必经框选/确认；自动回退须有真实选区证据；歧义不串栏；Esc/切窗取消；无截图落盘 |
| 3：专业能力 | 一个领域术语包，之后才是 RAG/代码解释 | 不污染通用词义，来源可查看，锁序不走 MT/LLM |

必要测试：路由状态与禁止回退、取消与 generation、UIA 候选早返回/有界搜索、复制期间前台变化、相同文本复制、剪贴板格式备份/恢复失败及并发修改、无真实选区不误收整行、OCR 区域坐标与取消。OCR 增加无选区拖动窗口不触发、跨行/双栏不以拖动两点矩形假装选区、只有坐标时可见行裁剪、指向空白不乱取邻栏、低分不静默漏行、符号/数字完整性和截图不落盘。单元测试用可控后端，系统 COM/剪贴板/OCR 另做隔离集成测试，不能只给 UIA/SendInput 打几个 mock 就宣布兼容。

人工矩阵：Chrome/Edge/Firefox、记事本、VS Code、Word/WPS、Acrobat/Edge PDF、ChatGPT 类 Electron/Chromium 应用、终端；测试鼠标拖选、双击、Shift+方向键、多行、长选区、文本 PDF、扫描 PDF、代码与数学符号。加上混合 DPI/负坐标、图片/富文本剪贴板、前台切换和权限拒绝。

每个场景记录自动取词、主动复制、OCR 三条路径的结果与误识情况。目标是消除无声失败和尽量覆盖支持范围，不把“有兜底入口”记成“准确识别成功”，也不在未测量前承诺成功率。
